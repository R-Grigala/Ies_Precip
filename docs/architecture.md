# არქიტექტურა და მონაცემთა ნაკადი

## კომპონენტების მიმოხილვა

```text
Browser
  ├── HTML/Jinja გვერდები და JavaScript
  └── REST API (/api)
          ├── SQLAlchemy ── MySQL
          └── JWT authentication

Scheduler process
  ├── Weather.com PWS API → მიმდინარე მაჩვენებლების განახლება
  ├── გრძელი დაგროვების გამოთვლა
  └── ისტორიული ჩანაწერების დამატება
```

### Flask აპი

[app.py](../app.py) აპის factory-ს იძახებს. [src/__init__.py](../src/__init__.py)-ის `create_app()` ქმნის Flask ობიექტს, რთავს CORS-ს, კითხულობს კონფიგურაციას და არეგისტრირებს SQLAlchemy, Flask-Migrate, Flask-RESTX და JWT გაფართოებებს. იქვე რეგისტრირდება გვერდების blueprints, CLI ბრძანებები და 404 handler.

REST რესურსები import-ისას რეგისტრირდება საერთო Flask-RESTX `Api` ობიექტის namespace-ებზე. Swagger UI ემსახურება `/api` მისამართზე.

### გვერდები და frontend

`src/views/` შეიცავს HTML გვერდების routes-ს, `src/templates/` — Jinja შაბლონებს, ხოლო `src/static/` — CSS, JavaScript და სურათებს.

- `/` — რუკის მთავარი გვერდი. რუკის კოდი არის `src/static/js/map/map.js`-ში და სადგურების პოზიციებს/მაჩვენებლებს API-დან იღებს.
- `/login`, `/accounts` — შესვლა და ანგარიშების გვერდები.
- `/filter` — ისტორიული მონაცემების ფილტრის გვერდი.
- `/stations` — სადგურების მართვის ინტერფეისი.
- `/reset_password/<token>` — პაროლის განახლების გვერდი.

გვერდების routes-ის არსებობა თავისთავად არ ნიშნავს, რომ ყველა გვერდი სერვერის მხარეს ავტორიზაციას ამოწმებს. ზოგი UI-ის წვდომის კონტროლი JavaScript-ით ხორციელდება; API-ს დაცვა ცალკე JWT დეკორატორებით არის განსაზღვრული.

### მონაცემთა შეგროვება და scheduler

[tools/scheduler.py](../tools/scheduler.py) scheduler-ის ცალკე პროცესია. ის ამოცანებს ასე გეგმავს:

| ამოცანა | ინტერვალი | შედეგი |
| --- | --- | --- |
| `update_temporary_db` | 1 წუთი | გარე PWS API-დან მიმდინარე მონაცემების წაკითხვა და `div_positions`-ის განახლება |
| `insert_precip_long_db` | 4 წუთი | გრძელვადიანი დაგროვების მნიშვნელობის გამოთვლა და `prev_precip` მდგომარეობის განახლება |
| `insert_precip_db` | 5 წუთი | მიმდინარე მნიშვნელობების ისტორიულ `weather_data` ჩანაწერებად შენახვა |

`run_scheduler.sh` ასრულებს `python tools/scheduler.py` ბრძანებას. Dockerfile-ის command scheduler-ს ფონურ პროცესად უშვებს და uWSGI-ს იწყებს.

#### მიმდინარე მნიშვნელობების განახლება

[update_temporary_db.py](../tools/update_temporary_db/update_temporary_db.py) თითოეულ `DivPositions` ჩანაწერს ამოწმებს. თუ სადგურის `fetch_status` გამორთულია, `xx:xx` მნიშვნელობებს წერს. თუ HTTP პასუხი წარმატებული არ არის, `--:--` მნიშვნელობებს წერს. წარმატებული პასუხიდან იღებს `precipRate` და `precipTotal` ველებს, ანგარიშობს რუკის ვიზუალურ სიმაღლეს და ბაზაში ინახავს.

#### გრძელი დაგროვება

[insert_precip_long_db.py](../tools/insert_precip_db/insert_precip_long_db.py) მიმდინარე დაგროვებას (`precip_accum`) ადარებს `PrevPrecip.prev_pa`-ს. თუ დაგროვება განულდა, იწყებს ნულოვანი პერიოდის აღრიცხვას; 24 საათის განმავლობაში ნულოვანი მაჩვენებლის შენარჩუნებისას `precip_accum_long` ნულდება. მნიშვნელობის ზრდისას მიმდინარე დაგროვებას ბოლო გრძელ მნიშვნელობას უმატებს; შემცირებისას ბოლო გრძელ მნიშვნელობას ინარჩუნებს. ეს ალგორითმი მონაცემის გარე წყაროს მრიცხველის ქცევაზეა დამოკიდებული.

#### ისტორიული ჩანაწერი

[insert_precip_db.py](../tools/insert_precip_db/insert_precip_db.py) `DivPositions`-იდან იღებს ჩანაწერებს, რომელთა `precip_accum` არ არის `xx:xx`, და თითოეულს `WeatherData` ჩანაწერად ამატებს. აქ ფილტრი `--:--`-ს არ გამორიცხავს.

## ავტორიზაციის მოდელი

შესვლისას მომხმარებლის UUID გამოიყენება JWT identity-ად. Access token-ის ვადა კონფიგურაციით 1 საათია, refresh token-ის — 12 საათი. მომხმარებლის როლში `is_admin` განსაზღვრავს ადმინისტრაციულ უფლებას. Login და პაროლის აღდგენის მოთხოვნა საჯაროა; მომხმარებლის მართვა და მონაცემების უმეტესობა JWT-ს მოითხოვს.

## განთავსება

Compose-ში MySQL, Flask/uWSGI და Nginx არიან. Nginx uWSGI პროტოკოლით უკავშირდება `flask:5000`-ს. Scheduler ცალკე Compose სერვისი არ არის — Flask კონტეინერის `CMD` მას ფონურ პროცესად უშვებს. წარმოებაში ამოცანების ცალკე პროცესად გაშვება უფრო საიმედო იქნება.
